## Отправная точка

Этапы 1–16 завершены. Модель уже:

- запускается локально и использует RX 6600 XT через Windows Ollama, с CPU
  fallback;
- читает очищенные состояния всех сущностей Home Assistant;
- по прямой команде владельца включает, выключает и переключает точный
  `switch`, нажимает точный `button`;
- для каждого действия обязана сама вызвать `ha_control_entity`, после чего
  оболочка делает фиксированный POST и повторный GET;
- не имеет произвольного shell, unrestricted HA service call или доступа к
  секретному токену.

Это остаётся рабочей базой. Требование владельца «не только читает, но и
взаимодействует со switch/button» уже является обязательным и не будет убрано.

## Что строим дальше

### Этап 17. Инвентаризация и стабильная идентичность

Собираем безопасную карту: HA entity → device → integration/config entry →
стабильный идентификатор (MAC/unique ID, где доступно) → текущий IP. Секретные
атрибуты и local keys модели не передаются.

Результат: агент отличает «тот же прибор получил новый IP» от «в сети появился
другой прибор».

### Этап 18. Быстрое обнаружение и журнал инцидентов

Добавляем постоянное WebSocket-наблюдение за HA и SQLite-журнал. Состояния:
`observed → confirmed → diagnosed → acted → verified → resolved/escalated`.
Один краткий `unavailable` не считается аварией: есть debounce, повторная
проверка, cooldown и дедупликация.

Результат: отказ датчика/реле замечается за секунды, а не на следующем
десятиминутном heartbeat.

### Этап 19. Детерминированная диагностика

Для каждого инцидента агент собирает свежий HA state, доступность HA API,
состояние интеграции и LAN-след устройства. Модель объясняет и выбирает только
из разрешённых планов; код проверяет факты и политику.

Результат: понятный диагноз с доказательствами, без догадок и ложных заявлений
«исправлено».

### Этап 20. Безопасное восстановление устройств и сменившегося IP

Лестница действий: обновить entity → перезагрузить точный config entry →
найти тот же device по стабильной идентичности → вызвать поддерживаемый
reconfigure конкретной интеграции → проверить возвращение сущностей.
LocalTuya/Tuya Local и другие интеграции получают отдельные адаптеры. Прямое
редактирование `.storage` и угадывание IP запрещены.

Результат: поддерживаемые устройства поднимаются после смены DHCP-адреса без
ручного вмешательства; неподдерживаемые безопасно эскалируются владельцу.

### Этап 21. Самоконтроль Home Assistant

Внешний watchdog различает: HA здоров, API завис, Core недоступен, HAOS-хост
недоступен. Если API жив, разрешается только лестница check-config → один
Core restart → ожидание → проверка. Для полностью мёртвого API отдельно
аудируем out-of-band канал; до этого автоматический reboot HAOS не включаем.

Результат: безопасное восстановление Core без циклов перезапуска; отсутствие
ложной гарантии при недоступном хосте.

### Этап 22. Режим дворецкого: свет, switch и button

Сохраняем текущие `switch`/`button`, добавляем `light.turn_on/off/toggle` и
ограниченные яркость/цвет. Точный объект должен быть однозначен; замки,
сигнализация, ворота и опасные реле остаются вне общей политики.

Результат: «включи свет в коридоре», точное управление розетками/реле и
кнопками с проверкой фактического состояния.

### Этап 23. Критические сообщения через Алису

Используем уже найденные две Яндекс.Станции и `tts.yandex_station_say`.
Сообщения строятся только из фактов инцидента. Добавляем уровень критичности,
quiet hours, дедупликацию, cooldown и dry-run. Входящие голосовые команды через
Алису остаются отдельным необязательным этапом после стабилизации автоматики.

Результат: при серьёзном отказе колонка сообщает, что сломалось, что агент
сделал и восстановилось ли устройство/HA.

### Этап 24. Проверка на аварийных сценариях и ввод в эксплуатацию

Тестируем: краткий обрыв, устойчивый `unavailable`, смену IP, неоднозначный
device, неудачный reload, плохую конфигурацию, зависший API, провал restart,
спам событий, недоступную колонку и prompt injection в атрибутах устройства.

Результат: автономные действия включаются только после доказанного fail-closed
поведения, полного журнала и повторной проверки результата.

## Допуск автоматических действий

Действие выполняется автоматически только если одновременно:

1. инцидент подтверждён повторными независимыми проверками;
2. устройство однозначно сопоставлено со стабильной идентичностью;
3. действие есть в узком allowlist для этой интеграции/сущности;
4. не исчерпан лимит попыток и прошёл cooldown;
5. действие обратимо или является безопасным штатным reload/restart;
6. после действия можно проверить результат;
7. все факты и действия записываются в журнал.

Если хотя бы одно условие не выполнено, агент ничего не меняет и уведомляет
владельца.
